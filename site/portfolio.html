Method — how a finding becomes a report

  1. Scope first, tooling second. Nothing is touched outside a program's written scope.
  2. Eligibility gate before writing. Extract the program's exclusions verbatim — out of scope, in scope but not eligible, open scope clauses, and its list of always-rejected finding classes — then match the finding against them. A real bug outside the rules is a rejected report.
  3. Avoid the word that gets you rejected. A panic triggered by one crafted input is an input-validation defect, not a denial of service.
  4. Check for AI / automated-scanning prohibitions in the policy before running any scanner.
  5. Reputation is an asset. Rejected or duplicate reports cost submission privileges on some platforms. Unverified findings are not submitted.
  6. Pre-submission checklist is a gate, not advice. Required fields, asset in scope, weakness mapping, severity consistent with the CVSS vector, reproducible steps, and a PoC that actually runs — all green before submission.
  7. Evidence standards. Executable PoC · negative controls that must fail and do fail · code citation with file and line numbers · raw tool output, not a retelling.
  8. Never overclaim. Severity is calculated, and where a score is arguable the conservative variant is stated alongside it.
  9. Name the attacker and the victim first. If the "victim" is the same principal who voluntarily installs the attacker's code at the same privilege level, an escalation of what that code can reach is hardening, not a vulnerability — it belongs in a pull request, not a report. Real boundary crossings need an unauthorised attacker (network-facing, missing authorization) or a different victim (another user, tenant, or server).

Mobile application security — eero (Amazon)

Report: HackerOne #4141935 · Status: closed as duplicate of #3665834 Assets: com.eero.android (Android) + app.eero.com

The eero Android app completes its SSO login by handing the user's real session token to the app over the custom URI scheme eero://jumpto/auth?token=<TOKEN>. The receiving activity is exported="true" and routes the /auth path to DeepLinkScreen$SsoResult with no scheme or host validation — the token is read straight from the URI and written into SecureTokenStorage, after which the session is treated as authenticated.

Two attack directions from one root cause:

  • Direction A — token theft to account takeover. Any installed app can declare the same eero://jumpto scheme and compete to receive the victim's real session token during a legitimate login. An attacker holding it controls the victim's home-network administration: network settings, connected devices, admins, and the Wi-Fi PSK.
  • Direction B — token injection to session fixation. Because V3DeepLinkActivity is exported, another app can start it directly with an explicit component, bypassing intent-filter matching entirely. The victim's app is switched into an attacker-controlled session, and eero's core setup flow then has the victim type their home Wi-Fi password into the attacker's account.

Key analytical finding: the developers demonstrably know how to bind a deep-link route to a verified host — RespondNetworkInvite$Companion.canHandle() checks host and path exactly against applinks.eero.com. The authentication route is simply not covered by that protection. This is a coverage gap, not a missing capability, which is why it was argued as worth a Critical assessment.

Evidence gathered (all public, passive, read-only):

  • https://app.eero.com/auth/index.html — HTTP 200, 1,875 bytes; its complete client-side logic builds the eero:// redirect verbatim
  • https://app.eero.com/.well-known/assetlinks.json — HTTP 200, 1,197 bytes; published and correctly binding com.eero.android to the release signing certificate, but governing only https links
  • Full exported-component audit of the APK (12 components) — everything else clean, documented so the report could not be misread as claiming more than was found

Report structure: root cause with exact smali locations, live transport proof, both attack directions with runnable PoC snippets, why the obvious mitigations do not apply, severity assessment with the argument against it stated plainly, honest limitations, and six specific remediation steps.

Outcome: closed as a duplicate — another researcher reported the same underlying issue first.

Smart contract security — Avail Bridge (Immunefi)

Market research — bounty landscape (20 Oct 2026)

Headline finding: the open-source bounty market is currently empty. Of ~561 issues labelled bounty, none were claimable. The three large audit platforms had no active contests.
