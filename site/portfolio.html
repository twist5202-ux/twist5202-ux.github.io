Method — how a finding becomes a report

  1. Scope first, tooling second. Nothing is touched outside a program's written scope.
  2. Eligibility gate before writing. Extract the program's exclusions verbatim — out of scope, in scope but not eligible, open scope clauses, and its list of always-rejected finding classes — then match the finding against them. A real bug outside the rules is a rejected report.
  3. Avoid the word that gets you rejected. A panic triggered by one crafted input is an input-validation defect, not a denial of service.
  4. Check for AI / automated-scanning prohibitions in the policy before running any scanner.
  5. Reputation is an asset. Rejected or duplicate reports cost submission privileges on some platforms. Unverified findings are not submitted.
  6. Pre-submission checklist is a gate, not advice. Required fields, asset in scope, weakness mapping, severity consistent with the CVSS vector, reproducible steps, and a PoC that actually runs — all green before submission.
  7. Evidence standards. Executable PoC · negative controls that must fail and do fail · code citation with file and line numbers · raw tool output, not a retelling.
  8. Never overclaim. Severity is calculated, and where a score is arguable the conservative variant is stated alongside it.
